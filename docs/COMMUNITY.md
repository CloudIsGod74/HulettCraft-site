# Community roster and banner screenshots

The Community directory is designed for all confirmed active members, including people without social channels. It is curated separately from online-player status: being offline does not make someone inactive, and a historical whitelist alone may contain former members.

## Editing the directory

Sign in through the existing **Admin** link using an allowlisted GitHub account, then choose **Manage member roster** on the Pending Screenshots page, or visit `/admin/roster` directly. No new account system or OAuth scopes are introduced.

Add a Minecraft username and display name for each confirmed member. Short bios and up to eight HTTPS social links are optional. “Show in directory” controls whether a profile is publicly visible; hidden entries remain editable. Removing a row is only published when you save. The editor warns about unsaved changes, retains edits after failed saves, and asks before saving an empty roster. Nothing is imported from online-player samples or Discord.

Saving updates the Community page without a rebuild. The existing `SESSION` KV namespace stores the roster under `public:community-roster:v1`, with no expiration, separately from session, revocation and favicon keys. No R2 objects are changed. If no roster has been saved, the initial list in `src/config/community.ts` is used (currently empty). Once saved, KV is the source of truth; changing that initial list will not overwrite the saved roster.

Administrator reads require the existing signed, allowlisted session. Writes also require the exact request Origin and validate the entire list before saving: a maximum of 200 unique Minecraft usernames, bounded display names/bios/links, and only HTTPS links without credentials. Invalid requests cannot partially replace the roster. Public rendering escapes all text, shows only active members, and announces new-tab links to assistive technology. The public page never serializes inactive records.

Storage errors disable initial editing and show an honest public unavailable message rather than treating failure as an empty roster. Failed writes retain the unsaved form. A revision check rejects observed stale edits with HTTP 409; **KV is eventually consistent and this is not an atomic multi-editor lock**. Use one editor at a time and allow about a minute for propagation. Concurrent global editing would need a transactional store such as a Durable Object or D1. Administrator responses and the Community page use `no-store`; don't override those headers with a CDN cache rule.

## Member images

Each profile can use initials (the existing default), a Minecraft skin head, or an uploaded image. Minecraft heads load directly from `https://mc-heads.net/avatar/<username>/128`, using the validated Minecraft username. This is a third-party image service, not Minecraft sign-in, identity verification, whitelist synchronization, or Discord integration. Choosing it sends the username to that service when a visitor loads the image; browser caching and the provider determine how quickly a changed skin appears. An unavailable image falls back to initials without hiding the profile.

For uploads, choose **Uploaded image** and select a PNG, JPEG, GIF or WebP up to 10 MiB. The editor decodes it, fits it within 256 × 256 and re-encodes a still WebP image before upload. Upload only images the member wants publicly displayed. The server independently enforces raster format, at most 512 × 512 and 96 KiB, and rejects SVG/HTML regardless of filename. Server validation recognizes raster structure rather than fully decoding pixels, consistent with existing screenshot validation. Failed uploads preserve the previous saved image. **Save roster** publishes the image choice; uploading alone does not publish a profile.

Images are content-addressed under `public:member-image:v1:<sha256>` in the existing `SESSION` KV namespace, separately from the small roster document. No new binding, R2 object, or screenshot-gallery entry is created. Repeated identical uploads reuse the same key. The authenticated `/api/admin/member-image` endpoint accepts uploads only with an exact Origin; its GET provides private, non-cacheable editor previews. The public directory embeds validated raster data URIs only for active profiles; there is no public arbitrary-key image endpoint. Image-read failures leave initials visible. Directory responses include the portrait bytes, so large rosters with many portraits increase page size. Old/unreferenced image keys are retained to avoid breaking saved references; there is no automatic cleanup or cross-environment migration.

Existing saved rosters without the optional `avatar` field continue to show initials. Images and roster settings use the environment's existing KV; isolate preview storage before editing real profiles.

## Gallery author choices and bulk editing

When signed in, HulettCraft season galleries and uploaded Hytale/Modded galleries offer a **Choose member** dropdown for each screenshot and a bulk-author toolbar. The dropdown uses all curated roster entries, including hidden former members for historical attribution, and saves the Minecraft username as the existing `author` text. Custom author text and existing names remain editable. Public gallery pages never include the administrator dropdown or hidden roster details. The bulk-upload table also has member choices per new image.

Select up to 50 published screenshots, choose a member or type an author, and choose **Apply author to selected**. Confirmation precedes replacement; an explicit checkbox and confirmation are required to clear an author. Only stored authors change. Image bytes, captions, content type and other custom metadata are preserved, and unsaved caption drafts remain in the editor. Each season's toolbar operates on its displayed screenshots. Static local gallery images are not editable R2 objects.

`POST /api/admin/bulk-metadata` requires the existing admin session and exact Origin. It validates the complete selection and action before writing, accepts only published world/season keys, and processes images sequentially with conditional ETag writes. R2 has no multi-object transaction: HTTP 207 reports individual failures, successful rows are deselected, and failed rows stay selected with their messages. A network failure may leave some writes completed; refresh and inspect before retrying. No invisible retries occur. The conditional write detects a change between reading and writing an object, not every edit since the page was first opened. Use one editor at a time.

The namespace binding must be available separately in each Pages environment. Before editing in a preview, confirm its `SESSION` namespace is isolated from production; previews sharing production KV can change the live roster. Automated tests use memory storage and generated local Wrangler state only. No real profiles, Discord invite, bot credentials, or Cloudflare settings have been added.

## Future Discord integration

The Discord invitation is still unknown, so the page retains the instruction to ask an administrator. Add the real invitation when supplied.

For future automation, first choose a trusted guild and membership/active role, then map stable Discord user IDs to Minecraft usernames. A server-side bot or scheduled sync can propose roster changes for administrator review while preserving bios, social links and manual overrides. Offline Minecraft players must not automatically become inactive. Avoid treating all Discord members or display names as a verified Minecraft roster. This would require a bot token, appropriate Discord member-list access and a defined sync policy; no Discord integration is enabled by this change.

## Screenshot banners

`src/config/banners.ts` defines curated existing local screenshots. Hytale pages use Hytale images; other pages use Minecraft images. A route-specific initial image renders even without JavaScript. In the browser, banners cycle every eight seconds, loading/decoding the next image before replacing the current one. Faint previous/next chevrons at the banner edges and horizontal touchscreen swipes provide manual cycling, wrap around the playlist and pause automatic rotation on the selected photo. Play resumes the eight-second rotation. There is no counter or extra control row. The arrows and small corner pause/play icon overlay the banner with transparent backgrounds and 44-pixel hit areas; keyboard focus makes controls more visible. Screen-reader feedback still announces manual selections. Swipe handling ignores interactive elements, small movements and multi-finger gestures; native vertical scrolling and pinch zoom remain available. Mouse dragging is not treated as a swipe. Pausing is remembered across pages in the current browser session, and rotation stops in hidden tabs. Controls stay hidden without JavaScript or when there is only one photo. Reduced-motion users start with a static image and may explicitly choose Play. Manual cycling skips unavailable alternatives and preserves the existing photo if none load; automatic cycling keeps the current photo when an alternative fails and tries the next on its following tick. Image decoding has an eight-second timeout so navigation cannot stay locked on a stalled request. Rapid taps cancel earlier fade cleanup before a newer photo is displayed. No R2 listings or gallery mutations are needed for this rotation. Add other approved screenshots to the configuration as desired.
